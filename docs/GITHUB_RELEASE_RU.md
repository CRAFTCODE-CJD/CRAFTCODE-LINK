# Выпуск CRAFTCODE LINK на GitHub

Репозиторий продукта — `CRAFTCODE-CJD/CRAFTCODE-LINK`. Обновление Windows использует публичный API последнего стабильного релиза этого репозитория. Настройка закреплена в `src/project-links.json`. Кнопка поддержки ведёт на Boosty и добавлена в `.github/FUNDING.yml`.

## Репозиторий

Опубликуйте проверенный исходный состав с LICENSE, THIRD_PARTY_NOTICES.md, licenses, third-party-sources, package-lock.json, .github и docs. Каталоги out и node_modules, профили и ключи исключены через .gitignore. Проверьте конечный список файлов перед первым коммитом. У SOURCE-архива есть отдельный FILES.sha256, который позволяет сравнить содержимое с соответствующими исходниками релиза.

В настройках публичного репозитория включите Issues и Private vulnerability reporting. Приватная ссылка из формы сообщения об ошибке работает после включения этого параметра. Workflow Check Windows source имеет право чтения, использует закреплённые версии действий и запускается для pull request, main и вручную. Его первый запуск на GitHub подтвердит работу на размещённом runner. [Приватные сообщения об уязвимостях](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-for-a-repository), [защита GitHub Actions](https://docs.github.com/en/actions/reference/security/secure-use).

## Сборка и проверка

Версия в package.json и package-lock.json должна совпадать. На чистом Windows-каталоге установите зависимости через `npm ci`, выполните `npm run check`, `npm test` и проверки нативных компонентов. BUILD-WINDOWS.cmd собирает приложение. Для установщика требуются Python 3.11+, Go и NSIS 3.11. Команда `node scripts/handoff.cjs --installer` создаёт переносной архив, исходники, список контрольных сумм и код обновления из собранного приложения. Имена и SHA-256 генерируются из версии пакета.

Запустите проверку упакованного EXE на временном профиле, проверьте перенос существующей истории и обновление предыдущего выпуска во временном каталоге. Сверьте байты упакованного src с исходниками выбранного коммита. В описание выпуска включите фактически выполненные проверки и открытые ограничения из QA_REPORT.md.

Сверьте изменённые экраны и действия со «Справкой LINK», первыми шагами и встроенными примерами на русском и английском. Обновите затронутые инструкции и субтитры. Перезапишите ролик и постер, если показанный экран или порядок действий изменился. Проверьте воспроизведение примеров из упакованной сборки и соответствие инструкции реальным действиям. Результат этой проверки входит в подготовку выпуска. [Поддержка справки](HELP_AND_FIRST_RUN_RU.md)

## Публичный релиз и обновление

Создайте тег `vX.Y.Z` на проверенном коммите. Соберите черновик релиза с таким же тегом и загрузите пять файлов.

| Файл | Назначение |
|---|---|
| `CRAFTCODE-LINK-X.Y.Z-Setup-x64.exe` | Установка и обновление Windows x64 |
| `CRAFTCODE-LINK-X.Y.Z-Portable-x64.zip` | Переносная сборка Windows x64 |
| `CRAFTCODE-LINK-X.Y.Z-Source.zip` | Соответствующие исходники и лицензии |
| `CRAFTCODE-LINK-X.Y.Z-SHA256SUMS.txt` | SHA-256 четырёх остальных файлов |
| `CRAFTCODE-LINK-X.Y.Z-Update-Code.txt` | Код ручного выбора обновления |

Перед публикацией скачайте загруженные файлы и сверьте контрольные суммы. Получите метаданные installer asset через GitHub API. Поле `digest` должно точно совпасть с `sha256:` и локальной суммой установщика. Проверьте размер, состояние `uploaded` и единственность installer asset с требуемым именем. [Метаданные release asset](https://docs.github.com/en/rest/releases/assets#get-a-release-asset).

Опубликуйте релиз как стабильный и последний, чтобы штатная проверка в LINK могла его найти. Черновики и prerelease скрыты от текущего обновления. Установщик определяется по точному имени и версии, а загрузка проверяется по размеру, сигнатуре EXE и SHA-256 из GitHub API. Открытый релиз сначала проверяется из предыдущей версии приложения на тестовом профиле. Одинаковая с текущим приложением версия отображается как актуальная. [Управление релизами](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository).

Опубликованный проверенный выпуск сохраняет свои файлы. Исправление бинарного содержимого оформляется следующей версией. Выпуск 0.7.14 пока не подписан Authenticode от имени разработчика: сертификат или одобренный сервис подписи ещё не подключён. Варианты, ограничения и порядок подписи Electron, помощников и NSIS описаны в [подготовке подписи релизов](CODE_SIGNING_RU.md). Контрольная сумма GitHub опирается на безопасность аккаунта издателя и HTTPS. [Текущая модель защиты](../SECURITY.md).

## Android

У Windows и Android будут отдельные установочные файлы и каналы доставки. Текущий проверяющий модуль Windows выбирает только Setup-x64.exe. Android требует своего подписанного приложения, постоянного идентификатора пакета и интеграции обновления со способом установки. Подготовка RuStore описана отдельно в RUSTORE_RELEASE_RU.md после проверки мобильной сборки.

# Выпуск CRAFTCODE LINK на GitHub

Репозиторий продукта — `CRAFTCODE-CJD/CRAFTCODE-LINK`. Обновление Windows использует публичную ссылку последнего стабильного релиза этого репозитория. Настройка закреплена в `src/project-links.json`. Кнопка поддержки ведёт на Boosty и добавлена в `.github/FUNDING.yml`.

## Репозиторий

Опубликуйте проверенный исходный состав с LICENSE, THIRD_PARTY_NOTICES.md, licenses, third-party-sources, package-lock.json, .github и docs. Каталоги out и node_modules, профили и ключи исключены через .gitignore. Проверьте конечный список файлов перед первым коммитом. У SOURCE-архива есть отдельный FILES.sha256, который позволяет сравнить содержимое с соответствующими исходниками релиза.

В настройках публичного репозитория включите Issues и Private vulnerability reporting. Приватная ссылка из формы сообщения об ошибке работает после включения этого параметра. Workflow Check Windows source имеет право чтения, использует закреплённые версии действий и запускается для pull request, main и вручную. Его первый запуск на GitHub подтвердит работу на размещённом runner. [Приватные сообщения об уязвимостях](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-for-a-repository), [защита GitHub Actions](https://docs.github.com/en/actions/reference/security/secure-use).

## Сборка и проверка

Для публичного выпуска под Windows x64 используйте Git, Node.js с npm, Python 3.11+, Go 1.25+, NSIS 3.11 и 7-Zip. Добавьте их в PATH. Пример из корня репозитория:

```powershell
python scripts/public-release.py v1.2.3 D:/LINK-Releases/v1.2.3 --signed-offline
```

Замените пример тега на выпускаемую версию. Чтобы подготовить файлы до создания тега, вместо него передайте полный SHA коммита, а затем поставьте тег на этот же коммит. Укажите новую папку назначения. Необязательный `--runtime-zip <путь>` принимает заранее скачанный Windows x64 архив Electron. При упаковке проверяется закреплённая сумма архива. Проверка истории перед сборкой использует локальный словарь из рабочей копии, в которой запущена команда. [Как настроить проверку приватности](PUBLICATION_PRIVACY.md)

Команда извлекает чистое дерево `git archive`, сверяет каждый файл с Git и устанавливает зависимости из `package-lock.json` через `npm ci`. Она запускает проверку синтаксиса и тесты, собирает приложение и вызывает штатные упаковщики. Перед выдачей файлов проверяются контрольные суммы, код обновления и полное соответствие Source.zip выбранному коммиту. Содержимое каталога приложения внутри NSIS сравнивается по файлам с Portable.zip. При `--signed-offline` сборщик дополнительно проверяет подпись шестого файла публичным ключом, сравнивает каждый байт вложенного EXE с установщиком и добавляет пакет в SHA256SUMS. Этот режим обязателен для официальных выпусков с поддержкой офлайн-пакетов. Для обычной сборки или форка без собственного ключа опустите флаг, чтобы получить прежние пять файлов.

`BUILD-WINDOWS.cmd` остаётся доступной для локальной сборки из рабочего дерева. Для отдельного установщика служит `python scripts/package-setup.py`, для набора готовых файлов — `node scripts/handoff.cjs --installer`.

Запустите проверку упакованного EXE на временном профиле, проверьте перенос существующей истории и обновление предыдущего выпуска во временном каталоге. Сверьте байты упакованного src с исходниками выбранного коммита. В описание выпуска включите фактически выполненные проверки и открытые ограничения из QA_REPORT.md.

Сверьте изменённые экраны и действия со «Справкой LINK», первыми шагами и встроенными примерами на русском и английском. Обновите затронутые инструкции и субтитры. Перезапишите ролик и постер, если показанный экран или порядок действий изменился. Проверьте воспроизведение примеров из упакованной сборки и соответствие инструкции реальным действиям. Результат этой проверки входит в подготовку выпуска. [Поддержка справки](HELP_AND_FIRST_RUN_RU.md)

## Ключ офлайн-пакетов

Подпись LINK подтверждает происхождение установщика при передаче пакета через другой компьютер или флешку. Проверяемая часть состоит из восьми ASCII-байтов `LINKUPD1` и строки `<версия> <размер EXE> <SHA-256 EXE>\n`. За ней следуют 384 байта подписи RSA-PSS с SHA-256 и солью из 32 байтов, затем один полный Setup. Подпись издателя, отображаемая самой Windows для EXE, оформляется отдельно через Authenticode.

Закрытый ключ находится в Microsoft Software Key Storage Provider в хранилище текущего пользователя Windows. CNG разрешает операции подписи и запрещает экспорт ключа. Публичная часть хранится в `src/offline-release-key.json` и попадает в приложение. Сборка требует совпадения открытой части и останавливается при отсутствии или подмене ключа. Проверяйте и собирайте только доверенные, просмотренные исходники в издательской учётной записи: процесс с правами этой записи может попросить CNG подписать данные.

При первом развёртывании нового издателя на его Windows-ПК выполните `powershell.exe -NoProfile -File scripts/offline-package.ps1 -Initialize` и включите полученный публичный JWK в проверенный коммит до сборки. Форк со своим издателем сначала выбирает собственное постоянное имя ключа в скрипте и свой публичный ключ. Повторная инициализация с существующим ключом проверяет совпадение. Появление нового закрытого ключа при уже закреплённой публичной части требует отдельного решения владельца.

Для восстановления предусмотрите системную резервную копию издательского ПК вместе с профилем Windows и заранее проверьте восстановление пробной подписи на изолированной машине. Одного файла JWK для восстановления закрытого ключа недостаточно. При плановой ротации сначала распространите сборку с новым закреплённым публичным ключом через уже доверенный канал. Её офлайн-переход со старого клиента требует пакета, подписанного прежним ключом. Обычный сборщик рассчитан на одно поколение и откажет при таком несовпадении. Альтернатива для перехода — официальный установщик из GitHub Releases. При утрате или компрометации прежнего ключа используйте независимый доверенный канал установки и сообщите пользователям о смене. До установки версии с новым ключом старые офлайн-клиенты сохраняют прежнее доверие.

## Публичный релиз и обновление

Создайте тег `vX.Y.Z` на проверенном коммите. Соберите черновик релиза с таким же тегом и загрузите проверенные файлы.

| Файл | Назначение |
|---|---|
| `CRAFTCODE-LINK-X.Y.Z-Setup-x64.exe` | Установка и обновление Windows x64 |
| `CRAFTCODE-LINK-X.Y.Z-Offline-x64.linkupdate` | Перенос официального обновления на другой ПК и проверка подписи внутри LINK |
| `CRAFTCODE-LINK-X.Y.Z-Portable-x64.zip` | Переносная сборка Windows x64 |
| `CRAFTCODE-LINK-X.Y.Z-Source.zip` | Соответствующие исходники и лицензии |
| `CRAFTCODE-LINK-X.Y.Z-SHA256SUMS.txt` | SHA-256 каждого из остальных файлов выпуска |
| `CRAFTCODE-LINK-X.Y.Z-Update-Code.txt` | Код ручного выбора обновления |

Перед публикацией скачайте загруженные файлы и сверьте контрольные суммы. Получите метаданные installer asset через GitHub API. Поле `digest` должно точно совпасть с `sha256:` и локальной суммой установщика. Проверьте размер, состояние `uploaded` и единственность installer asset с требуемым именем. [Метаданные release asset](https://docs.github.com/en/rest/releases/assets#get-a-release-asset).

Опубликуйте релиз как стабильный и последний, чтобы штатная проверка в LINK могла его найти. Черновики и prerelease скрыты от текущего обновления. Клиент получает тег через публичную ссылку releases/latest. Если версия новее, клиент берёт SHA-256 из файла Update-Code.txt того же тега и размер установщика по HTTPS. Загрузка проверяется по размеру, заголовку EXE и SHA-256. Проверка актуальной версии требует одного запроса HEAD. Открытый релиз сначала проверяется из предыдущей версии приложения на тестовом профиле. Одинаковая с текущим приложением версия отображается как актуальная. [Управление релизами](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository).

Опубликованный проверенный выпуск сохраняет свои файлы. Исправление бинарного содержимого оформляется следующей версией. Выпуск 0.7.14 пока не подписан Authenticode от имени разработчика: сертификат или одобренный сервис подписи ещё не подключён. Варианты, ограничения и порядок подписи Electron, помощников и NSIS описаны в [подготовке подписи релизов](CODE_SIGNING_RU.md). Контрольная сумма GitHub опирается на безопасность аккаунта издателя и HTTPS. [Текущая модель защиты](../SECURITY.md).

## Android

У Windows и Android будут отдельные установочные файлы и каналы доставки. Текущий проверяющий модуль Windows выбирает только Setup-x64.exe. Android требует своего подписанного приложения, постоянного идентификатора пакета и интеграции обновления со способом установки. Подготовка RuStore описана отдельно в RUSTORE_RELEASE_RU.md после проверки мобильной сборки.
